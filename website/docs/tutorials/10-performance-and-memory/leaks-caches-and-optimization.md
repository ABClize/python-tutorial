# 泄漏、缓存与优化顺序

内存持续增长不一定来自垃圾回收失效。更常见的情况是对象仍然被程序需要或意外持有，例如无界列表、
缓存、积压队列、未完成任务和没有注销的监听器。

## 无界容器会随运行时间增长

```python
events: list[dict[str, object]] = []


def record_event(event: dict[str, object]) -> None:
    events.append(event)
```

只追加、不删除的全局列表会随事件数量持续增长。字典、历史记录、日志缓冲和队列也有同样问题。

解决方式取决于用途：

- 只需要最近数据：使用固定容量或按时间清理；
- 数据需要长期保留：写入数据库或文件，不放在进程内存中无限累积；
- 队列用于异步处理：设置容量、背压、超时和拒绝策略；
- 用于统计：保存聚合结果，而不是保存全部原始事件。

垃圾回收器不会清理 `events` 中的对象，因为全局列表仍然可以访问它们。

## 生产速度高于消费速度

即使每个消息处理完都能释放，当生产者长期比消费者快时，队列仍会持续增长。此时需要同时观察：

- 队列当前长度和增长速度；
- 消息进入与处理速率；
- 单条消息平均大小；
- 消费失败和重试数量；
- 消费者并发上限。

扩容消费者只是一个选择。还可能需要降低生产速率、批量处理、丢弃过期任务，或把压力反馈给上游。

## 任务、异常和监听器也会保留对象

尚未完成的 Task、Future 和协程会保存调用状态，其中可能包含大型局部变量。异常 traceback 也可能
引用完整调用栈。

事件总线保存绑定方法时，会间接保存方法所属的实例：

```python
listeners.append(service.handle_event)
```

如果实例结束使用后没有注销监听器，`listeners` 仍使它可达。排查这类问题要观察未完成任务数量、
回调注册数量和对象生命周期，而不是反复调用垃圾回收。

## 缓存用空间换时间

`lru_cache` 可以保存纯函数的结果：

```python
from functools import lru_cache


@lru_cache(maxsize=128)
def fibonacci(number: int) -> int:
    if number < 2:
        return number
    return fibonacci(number - 1) + fibonacci(number - 2)


print(fibonacci(10))
print(fibonacci.cache_info().currsize <= 128)
```

运行结果：

```text
55
True
```

`maxsize=128` 限制最多保留 128 个最近使用的键。`@cache` 和
`@lru_cache(maxsize=None)` 不限制条目数，输入空间不断扩大时，内存也可能不断增长。

加入缓存前需要回答：

- key 是否完整表示所有计算输入；
- 参数是否可哈希；
- 最大容量是多少；
- 结果是否需要过期；
- 外部数据变化时怎样失效；
- 空结果和异常是否应该缓存；
- 多个请求同时未命中时怎样避免重复重算；
- 缓存内容是否包含敏感数据。

`cache_info()` 可查看命中、未命中、容量和当前条目数，`cache_clear()` 可清空缓存。数据库或远程接口
结果通常还需要 TTL、数据版本或主动失效策略，不能只依赖进程内 LRU。

## 优化通常从减少工作开始

常见优先级如下：

1. 删除不必要工作和重复计算；
2. 减少重复网络、数据库和磁盘 I/O；
3. 选择更合适的算法和数据结构；
4. 使用批量接口，减少跨进程或跨网络往返；
5. 缓存稳定、重复且计算成本高的结果；
6. 减少不必要的对象分配；
7. 最后再考虑局部语句的微小差异。

把重复 list 查询换成 set，可能把 O(n²) 降到平均 O(n)；一次批量查询可能替代上千次数据库往返。
这类改变通常比缩短某个循环的写法更有价值。

每次修改后都要重新检查结果、顺序、异常和副作用。运行更快但少处理了数据，不是有效优化。

## CPU 密集与 I/O 密集

I/O 密集程序的大部分时间在等待网络、数据库或文件。线程或 asyncio 可以让多个等待过程重叠，
提高并发处理能力，但不会让单次外部请求本身变快。还需要连接池、超时、并发上限和背压。

CPU 密集程序长时间执行 Python 计算。应先检查算法和重复工作。受 CPython 全局解释器锁影响，增加
线程通常不能让纯 Python CPU 计算按核心数线性加速。

CPU 密集任务可能考虑：

- 多进程；
- NumPy 等在原生代码中执行的向量化操作；
- 专用原生扩展；
- 独立工作进程。

并行也有进程启动、序列化、进程间通信和内存复制成本，小任务不一定更快。

## 服务性能要观察尾延迟

| 指标 | 含义 |
| --- | --- |
| p50 | 中位请求延迟 |
| p95 | 95% 请求不超过的延迟 |
| p99 | 99% 请求不超过的延迟 |
| RPS | 每秒完成的请求数 |
| 错误率 | 请求失败比例 |
| 并发数 | 同时处理或等待的请求数量 |

平均值会掩盖少量非常慢的请求。垃圾回收停顿、锁竞争、连接池等待、慢查询和外部依赖长尾，可能主要
影响 p95 或 p99。

各工具回答的问题不同：

- `timeit` 比较受控的局部实现；
- `cProfile` 查找单进程 Python 调用热点；
- 负载测试观察并发下的吞吐和延迟；
- 生产监控观察真实输入、真实依赖和长期变化。

## 记录基线与复测

| 项目 | 应记录的内容 |
| --- | --- |
| 问题表现 | 哪个操作慢，或哪个内存指标增长 |
| 衡量指标 | 耗时、吞吐、p99、Python 堆或 RSS |
| 环境 | Python、依赖、操作系统和硬件 |
| 输入 | 规模、分布和构造方式 |
| 基线 | 修改前的重复测量结果 |
| 热点证据 | profile、快照或追踪位置 |
| 修改 | 本次改变的单一因素 |
| 正确性 | 测试和结果一致性 |
| 复测 | 与基线相同的条件 |
| 取舍 | 内存、可读性、一致性或复杂度成本 |

没有基线与复测的“优化”只是一次代码改动；没有正确性验证的更快结果，可能只是在少做工作。

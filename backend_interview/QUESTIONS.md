# 现代 Python 后端项目面试题

回答时建议固定使用“结论 → 原理 → 项目取舍 → 失败场景”的结构。

## FastAPI

### 1. `async def` 路由一定比普通 `def` 快吗？

- 不一定；收益来自等待异步 I/O 时让出事件循环。
- 普通 `def` 路由会在线程池执行，适合同步阻塞库。
- 在 `async def` 中直接调用阻塞 I/O 会卡住整个事件循环。

### 2. FastAPI 的依赖注入解决什么问题？

- 把认证、数据库会话、配置和服务构造从路由业务逻辑中分离。
- 同一依赖默认在单个请求内缓存，子依赖形成有向依赖图。
- 测试可通过 `app.dependency_overrides` 替换昂贵或外部依赖。

### 3. 为什么推荐 `Annotated[T, Depends(...)]`？

- 业务类型仍然是 `T`，元数据单独放在 `Annotated` 中。
- 编辑器和静态类型检查器能保留更准确的类型信息。
- 类型别名可以复用复杂依赖声明。

### 4. `yield` 依赖适合哪些资源？

- 数据库会话、事务、临时文件、锁或审计上下文。
- `yield` 前是获取资源，`finally` 中保证释放。
- 一个依赖应只 `yield` 一次，异常路径也必须清理。

### 5. lifespan 和旧的 startup/shutdown 事件有什么区别？

- lifespan 用一个异步上下文管理器描述启动和关闭的完整生命周期。
- 更容易保证资源成对创建/释放，也便于测试。
- 不应同时混用 lifespan 与旧事件处理方式。

### 6. 中间件和依赖应该如何选择？

- 中间件适合请求 ID、耗时、通用日志等所有请求的横切逻辑。
- 依赖适合需要解析参数、权限判断或向路由注入值的逻辑。
- 中间件包围整个请求，依赖只作用于声明它的应用/路由/端点。

### 7. `response_model` 有什么价值？

- 验证并过滤输出，避免内部字段或密码意外泄露。
- 生成准确的 OpenAPI Schema。
- 还能将 ORM/领域对象转换为稳定的 API 契约。

### 8. 为什么不应该直接在路由中写数据库逻辑？

- 路由会同时承担 HTTP、业务规则和持久化职责，难以测试和复用。
- 服务层负责用例编排，仓储层负责持久化边界。
- 分层不是为了文件数量，而是为了隔离变化。

### 9. 422、400、409 分别适合什么场景？

- 422：请求结构或字段语义验证失败。
- 400：通用客户端请求错误。
- 409：资源当前状态冲突，例如幂等、状态转换或乐观锁冲突。

### 10. 如何设计统一错误响应？

- 领域层抛与 HTTP 无关的异常。
- API 边界通过异常处理器映射状态码和稳定错误码。
- 响应包含 request ID，日志记录完整内部细节但不泄露给客户端。

### 11. FastAPI 中如何实现认证与授权？

- 认证回答“你是谁”，授权回答“你能做什么”。
- 认证依赖解析 token/API key 并返回 Principal。
- 更细粒度的角色/权限可以作为认证依赖的子依赖。

### 12. BackgroundTasks 适合可靠任务队列吗？

- 不适合；它与应用进程同生共死，没有持久化、重试和跨实例协调。
- 适合轻量、失败可接受的响应后工作。
- 关键任务应使用持久化队列和 outbox 等机制。

### 13. 如何测试 FastAPI 路由？

- 同步测试可使用 `TestClient`。
- 异步测试可用 HTTPX `AsyncClient + ASGITransport`。
- 涉及 lifespan 时要用 `TestClient` 上下文或显式 lifespan 管理器。

### 14. OpenAPI 文档与真实行为不一致通常是什么原因？

- 没有声明 `response_model` 或错误响应模型。
- 动态返回不同结构但缺少联合类型。
- 中间件/异常处理器改变了响应，却没有在路由文档中声明。

### 15. 如何实现分页？

- offset/limit 简单但深分页成本高，数据变动时结果可能漂移。
- cursor/keyset 分页更适合大表和稳定顺序。
- 必须定义唯一、稳定的排序键。

## Pydantic v2

### 16. Pydantic 的核心职责是什么？

- 在系统边界把不可信输入解析为有类型、经过验证的数据。
- 同时提供序列化和 JSON Schema。
- 它不能替代领域层中跨聚合、需要 I/O 的业务规则。

### 17. `model_validate` 和直接构造有什么差别？

- 都执行验证；`model_validate` 更适合已有字典或对象。
- `model_validate_json` 可以直接解析 JSON 字节/字符串。
- v2 中应使用 `model_dump`/`model_dump_json` 替代 v1 的 `dict`/`json`。

### 18. `field_validator` 的 before 和 after 如何选择？

- before 接收原始输入，适合兼容旧格式或预处理。
- after 接收已完成类型解析的值，类型更安全。
- 无论哪种模式都必须返回要继续使用的值。

### 19. 什么情况应该使用 `model_validator`？

- 两个以上字段之间存在约束，例如两次密码必须一致。
- after 模式以完整模型实例工作。
- 不要在 validator 中发网络请求或数据库查询。

### 20. `extra="forbid"` 有什么价值？

- 输入拼错字段时立即失败，避免悄悄丢数据。
- 对外部写请求尤其有用。
- 对兼容性要求高的读取模型可以选择 ignore/allow。

### 21. strict mode 的取舍是什么？

- 禁止 `"123"` 自动转换为数字，能更早发现上游契约错误。
- 对 HTTP 输入可能降低易用性，需要结合 API 契约决定。
- 财务、审计和内部事件模型通常更适合严格模式。

### 22. `from_attributes=True` 用于什么？

- 从对象属性而不是字典读取数据，常用于 ORM/领域对象响应。
- 它只解决读取，不应让 Pydantic 模型承担数据库职责。
- 是 v2 中替代 `orm_mode` 的配置。

### 23. 判别联合为什么优于普通 Union？

- 根据固定 discriminator 字段直接选择分支。
- 错误信息更准确，性能和 OpenAPI 表达也更清晰。
- 适合支付方式、领域事件等多态输入。

### 24. TypeAdapter 适合什么场景？

- 验证 `list[Model]`、联合、TypedDict 等非 BaseModel 根类型。
- 可以复用验证和 JSON Schema，而不必创建包装模型。
- 高频路径可复用同一个 adapter，避免重复构建 schema。

### 25. `RootModel` 与普通模型的区别？

- RootModel 表示顶层本身就是列表、字典或标量。
- 序列化结果不会额外包一层字段名。
- 对公共 API 是否使用顶层数组仍要考虑未来扩展性。

### 26. SecretStr 能保证密码安全吗？

- 不能；它只在 repr/日志中遮罩内容。
- 传输要用 TLS，存储要使用专门的密码哈希算法。
- 调用 `get_secret_value()` 后仍需避免记录明文。

### 27. 可变默认值应该怎么写？

- Pydantic 会智能复制许多不可哈希默认值，但显式 `default_factory` 更清晰。
- 普通 Python 函数和 dataclass 同样应避免共享可变默认值。
- 时间戳、UUID 等动态值必须使用 factory。

### 28. computed_field 与 property 有什么区别？

- computed_field 会进入 Pydantic 序列化和 JSON Schema。
- 普通 property 只在 Python 对象访问时存在。
- 计算昂贵时要考虑缓存和 N+1 问题。

### 29. field_serializer 适合什么场景？

- 自定义时间、金额、枚举等输出格式。
- 验证与序列化是两个方向，不应混在一个 validator 中。
- 公共格式变化属于 API 契约变化。

### 30. BaseSettings 应该何时创建？

- 通常在进程启动时创建一次，失败就快速终止。
- 测试通过依赖覆盖或直接注入 Settings，避免污染系统环境。
- `.env` 适合本地开发，生产秘密应由平台注入。

## asyncio

### 31. coroutine、Task 和 Future 有什么区别？

- coroutine 是可暂停函数调用产生的对象。
- Task 把 coroutine 调度到事件循环执行。
- Future 是表示未来结果的更底层 awaitable，业务代码通常不直接创建。

### 32. `gather` 与 TaskGroup 的关键区别？

- gather 结果顺序与输入一致，但一个任务失败时不会自动取消其他任务。
- TaskGroup 提供结构化并发，一个非取消异常会取消兄弟任务并等待清理。
- 关联任务要“同生共死”时优先 TaskGroup。

### 33. 为什么不能吞掉 CancelledError？

- 超时、TaskGroup 和服务关闭依赖取消传播。
- 协程应在 `finally` 清理后重新抛出取消。
- 吞掉取消会导致任务泄漏和关闭超时。

### 34. `asyncio.timeout()` 如何工作？

- 超时时先取消当前任务，再在上下文管理器外转换为 TimeoutError。
- 因此 TimeoutError 要在 `async with` 外捕获。
- 下游必须正确响应取消，否则实际耗时可能超过期限。

### 35. 为什么需要 Semaphore？

- 限制同时访问数据库、HTTP 上游或文件句柄的任务数。
- 防止突发请求耗尽连接池和内存。
- 它限制并发，不等于每秒请求速率限制。

### 36. asyncio.Lock 能防止线程竞争吗？

- 不能；它只协调同一事件循环中的协程。
- 多线程使用 threading.Lock，多进程需要进程安全原语或外部协调。
- 即使单线程，跨 await 的读改写也可能产生协程竞争。

### 37. 在 async 路由中调用 requests/time.sleep 会怎样？

- 它们会阻塞事件循环，所有共享该循环的请求都受影响。
- 应使用异步客户端/asyncio.sleep，或用 `to_thread` 迁移阻塞 I/O。
- CPU 密集任务通常应放到进程池或任务系统。

### 38. `asyncio.to_thread` 适合 CPU 密集任务吗？

- 通常不适合纯 Python CPU 任务，因为 GIL。
- 适合同步阻塞 I/O，或会释放 GIL 的扩展库。
- CPU 任务可考虑进程池、原生扩展或独立 worker。

### 39. Queue 的 `task_done` 和 `join` 如何配合？

- 每次成功 `get` 都必须最终调用一次 `task_done`。
- `join` 等待未完成计数归零，不是等待 worker 退出。
- worker 退出通常还需要 sentinel 或显式取消。

### 40. 什么是 backpressure？

- 当消费者跟不上生产者时，系统主动限制生产速度。
- 有界 Queue、Semaphore、连接池和限流都是实现方式。
- 无界队列只是把过载转化为内存增长和更高延迟。

### 41. first-success 模式有哪些清理要求？

- 第一个成功后必须取消并等待剩余任务。
- 所有任务失败时要保留有意义的异常信息。
- 不能只返回而遗留后台任务。

### 42. 如何实现异步重试？

- 只重试明确的瞬时错误，设置次数、退避、抖动和总截止时间。
- 每次重试必须考虑幂等性。
- CancelledError 不应该被普通重试捕获。

### 43. fire-and-forget 任务有什么风险？

- 事件循环只持有 task 的弱引用，任务可能丢失或异常无人观察。
- 应保存强引用、记录异常并在关闭时等待/取消。
- 关键业务任务应使用可靠队列。

### 44. 如何防止缓存击穿？

- 同一个 key 的并发未命中合并成一次上游请求，即 single-flight。
- 锁内要二次检查缓存。
- 还需要 TTL 抖动、错误缓存策略和容量限制。

### 45. ContextVar 为什么适合 request ID？

- 每个异步任务有独立上下文，不会像全局变量一样串请求。
- 创建子任务时上下文会复制。
- 在线程/进程边界传播仍需要显式设计。

## 架构、数据与可靠性

### 46. Repository Protocol 有什么价值？

- 服务层依赖持久化能力的抽象，而不是具体数据库。
- Fake 仓储让业务测试快速、确定。
- 不应为了“解耦”把每个简单查询都包装成无意义接口。

### 47. 为什么还要数据库唯一约束，应用里不是已经检查幂等键了吗？

- “先查再写”在并发下存在竞态。
- 数据库唯一约束是最终一致性边界。
- 冲突后读取已有结果，才能真正实现幂等。

### 48. 乐观锁适合什么场景？

- 冲突少、读取多、更新短的场景。
- 更新条件包含版本号，影响行数为 0 表示冲突。
- 冲突后由客户端重读、合并或重试，不能静默覆盖。

### 49. 幂等键应该保存多久？

- 至少覆盖客户端可能重试的窗口。
- 通常保存请求指纹、状态码和响应，防止同一键用于不同请求。
- 过早清理会重复执行，永久保存则带来容量问题。

### 50. 什么是 transactional outbox？

- 业务数据和待发布事件写入同一个数据库事务。
- 独立发布器读取 outbox 并发送，避免“数据库成功、消息发送失败”。
- 消费者仍需幂等，因为消息可能重复。

### 51. 什么时候需要 Unit of Work？

- 一个用例跨多个仓储并要求统一事务边界时。
- UoW 管理 begin/commit/rollback，不应由路由直接控制。
- 简单单表操作不必为了模式而增加复杂度。

### 52. 缓存旁路模式有什么一致性问题？

- 写数据库与删缓存之间可能出现短暂不一致。
- 并发读可能把旧值重新写回缓存。
- 要根据业务选择失效、版本、消息通知或接受最终一致。

### 53. 如何设计外部服务超时？

- 入口有总 deadline，下游调用分配更短预算。
- 连接、读取和整体超时应区分。
- 超时后取消无用工作，并把错误映射为可观测的稳定错误码。

### 54. Circuit Breaker 解决什么问题？

- 上游持续失败时快速失败，防止线程/连接被耗尽。
- 状态通常包括 closed、open、half-open。
- 它不是重试的替代品，两者组合不当会放大流量。

### 55. 如何避免重试风暴？

- 指数退避加随机抖动。
- 限制总次数和总 deadline。
- 只在幂等操作或带幂等键的操作上重试。

### 56. 请求 ID 应在哪里生成和传播？

- 入口中间件接受可信上游 ID 或生成新 ID。
- 日志、下游 HTTP、消息元数据都携带它。
- 不能把 request ID 当安全凭据。

### 57. 单元测试、集成测试、端到端测试如何分工？

- 单元测试覆盖服务规则和边界，快速且数量最多。
- 集成测试验证数据库、HTTP 客户端、序列化等真实边界。
- E2E 少而关键，验证部署后的主路径。

### 58. 为什么测试要覆盖依赖覆盖机制本身？

- 防止测试意外访问真实认证或外部服务。
- 每个测试后要清空 overrides，避免全局状态泄漏。
- 至少保留少量真实依赖集成测试。

### 59. Fake、Mock、Stub 如何选择？

- Stub 返回固定结果；Mock 还验证交互；Fake 提供轻量可工作实现。
- 领域测试常用 Fake 仓储，外部错误分支适合 Mock/Stub。
- 过度验证调用细节会让重构成本很高。

### 60. 生产部署 FastAPI 要关注什么？

- 多 worker、反向代理、超时、优雅关闭和健康检查。
- 每个 worker 都有独立内存，进程内缓存和锁不能跨 worker。
- 数据库连接池大小要乘以 worker 数评估。
